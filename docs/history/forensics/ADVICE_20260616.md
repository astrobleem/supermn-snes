## BLOCKER 1 — Not a bug. The map mode byte $30 is correct.

The central claim is wrong:

> Expected value for LoROM+FastROM: $21

$21 is **HiROM (slow)**, not LoROM+FastROM. The map-mode byte encodes the
mapping in the low nibble and the speed bit ($10) separately:

```
$20 = LoROM, slow ROM (2.68 MHz)
$30 = LoROM, fast ROM (3.58 MHz)   <- bit $10 set = FastROM
$21 = HiROM, slow ROM
$31 = HiROM, fast ROM
```

So WLA-DX's "info_bits = 32 ($20) base, +16 ($10) for FastROM = 48 ($30)" is
**exactly right**. There is no WLA-DX bug here.

The 12 commercial ROMs read $20 because they are slow-ROM LoROM titles — I
confirmed all of them read `$20` at `$7FD5`. They are not a counterexample to
$30; they simply aren't FastROM games.

### The real issue is internal inconsistency in *your* project
- Your code enables FastROM at runtime: `sta MEMSEL` with `#$01` (main.pasm:138,
  main.65816:116).
- But `build_rom.py:17` writes `$20` (slow) into the header.
- And `main.65816:228` / `fix_header.py:6` write `$02`, which is **not a valid
  map mode at all** ($02 would read as an invalid/SuperFX-ish mode; it is not
  "LoROM+FastROM"). This is a genuine bug — just not WLA's.

**Recommendation:** decide one thing and make all three agree.
- If you want FastROM (you seem to, given `MEMSEL=$01`): write **`$30`**.
- If you want to keep it simple/slow: write **`$20`** and set `MEMSEL=$00`.

Either boots in every emulator. The header byte is informational; `$420D`
(MEMSEL) is what actually controls bus speed on hardware. Just stop writing
`$02`.

## BLOCKER 2 — Not a WLA linker bug. The header is placed wrong.

Two separate mistakes are creating the "overlap" and the "origin overflow":

**1. The header is 16 bytes too long / starts in the wrong place.**
In `main.65816:218` you do `.org $7FC0` and then emit the *extended* header
first: maker code (2) + game code (4) + 7 reserved + 3 more = 16 bytes, **then**
the 21-byte title. That pushes the title to $7FD0 and the map-mode byte to
~$7FE5 — straight into the vector region. That is your "overlap."

The extended header block (maker/game code) lives at **$FFB0–$FFBF**, and the
**title must start at exactly $FFC0**. So either:
- Drop the extended block and start the title at $FFC0, or
- Put the extended block at $FFB0 and the title at $FFC0.

**2. `.org $7FC0` uses the *file offset* as a CPU address.**
Your MEMORYMAP puts slot 0 at CPU `$8000–$FFFF`. CPU address `$7FC0` is below
the slot, hence "Origin overflows from bank." In LoROM bank 0, **file offset
$7FC0 = CPU address $FFC0**. Use `.org $FFC0` (and `$FFE0`/`$FFF0` for vectors),
not `$7FC0`. The $7Fxx numbers are file offsets, not CPU addresses.

**Recommendation:** This is all fixable in WLA-DX if you ever want to use it.
But see Blocker 4 — you don't need to. WLA-DX is not broken here.

## BLOCKER 3 — Misdiagnosis. Poppy is fine; your hardcoded vectors are wrong.

This is the most important finding. I disassembled the actual shipped binary.

**Poppy resolves labels correctly.** In `distribution/superman.sfc`:
- `$FFFC` (RESET) = `$8000` → `hw_reset` is at file $0000 = CPU $8000. Correct.
- `$FFEA` (NMI) = `$801C` → `nmi_handler` is at file $001C = CPU $801C. Correct.

Both of those are label-resolved (`.word nmi_handler`, `.word hw_reset`) and
both are dead-on. There is no off-by-N in Poppy's LoROM label resolution.

**Your hardcoded vectors are the bug.** In the actual binary the three tiny
handlers sit in a run of `rti` ($40) bytes:
```
file $0032  CPU $8032  = rti   (tail of NMI's own rti)
file $0033  CPU $8033  = rti   irq_handler
file $0034  CPU $8034  = rti   cop_handler
file $0035  CPU $8035  = rti   brk_handler
```
But main.pasm hardcodes (lines 222–227):
```
.word $8033   ; COP  -> actually cop_handler is $8034   (off by -1)
.word $8034   ; BRK  -> actually brk_handler is $8035   (off by -1)
.word $8032   ; IRQ  -> actually irq_handler is $8033   (off by -1)
```
Every one of them points one byte early. It "works" purely because the targets
land inside a contiguous block of `rti` bytes — any byte in that run happens to
be a valid `rti`. The moment you add or reorder a handler, this silently breaks.

**Where the misdiagnosis came from:** the "evidence" in BLOCKER 3 (cop=$8000,
the symbol table) is from `build/superman.sym`, which is a **WLA-DX** symbol file
for `main.65816` — a *different source file with a different handler order*
(cop/brk/irq at $8000/$8001/$8002). You compared Poppy's output against WLA's
symbol table for a different file and concluded Poppy was off. It wasn't.

**Recommendation:** revert to labels and delete the hardcoding:
```
.word cop_handler   ; $FFE4
.word brk_handler   ; $FFE6
.word irq_handler   ; $FFEE   (etc.)
```
Then verify (non-destructive): rebuild and check the vector bytes:
```
make && xxd -s 0x7FE0 -l 32 distribution/superman.sfc
```
COP should read `34 80`, BRK `35 80`, IRQ `33 80`. If they do (they will),
Blocker 3 is closed and you've removed a real latent bug.

## BLOCKER 4 — Build is fine. Just delete the dead, buggy script.

The two-step `Poppy → build_rom.py` pipeline is clean and deterministic. There
is nothing fragile about generating a fixed-format header in Python; plenty of
production homebrew does exactly this. I would not chase a single-assembler
solution unless WLA's section/bank features become necessary later.

**`fix_header.py` is dead code and it is wrong** — delete it:
- It is **not in the makefile** (only `build_rom.py` runs). It never executes.
- It writes the invalid `$02` map byte (see Blocker 1).
- It writes the checksum fields **in the wrong order**: it puts the checksum at
  `$7FDC` and the complement at `$7FDE`. The standard (and what `build_rom.py`
  correctly does, and what Doom does — I checked) is **complement at $FFDC,
  checksum at $FFDE**. So `fix_header.py` would corrupt a correct ROM.

Keeping a broken, unused script around is how someone "fixes" the build six
months from now by running it and breaks everything. Remove it.

**Minor inconsistencies worth tidying (non-blocking):**
- ROM-size byte is `$08` (= 256 KB) but the file is 64 KB; `poppy.json` declares
  2 MB. Harmless to emulators, but pick honest numbers.
- `poppy.json` declares 64 KB SRAM and SA-1; the header writes `$00` SRAM and
  cart type `$00` (ROM only). Reconcile when you actually wire up SA-1/SRAM.

## BLOCKER 5 — Correctly resolved; the write-up is just muddled.

Your conclusion ("checksum + complement = $FFFF is the only check that matters")
is right. The paragraphs of byte-sum arithmetic are a red herring. The clean
statement of the algorithm:

1. Zero the 4 checksum-field bytes ($FFDC–$FFDF).
2. `S = (sum of all ROM bytes) mod 0x10000`.
3. Write **complement** `= S XOR 0xFFFF` at `$FFDC` (little-endian).
4. Write **checksum** `= S` at `$FFDE` (little-endian).

The only invariant that means anything is `checksum + complement == 0xFFFF` as
16-bit words. I verified this holds for Doom (`chk=$B564`, `comp=$4A9B`,
sum=$FFFF) and for your shipped ROM (`chk=$6565`, `comp=$9A9A`). `build_rom.py`
implements this correctly.

The "total byte sum equals the checksum value" observation is a coincidence and
should be dropped from the notes — it confuses more than it explains.

**On your reviewer question:** no, essentially no emulator refuses to boot on a
bad checksum. bsnes/higan/Mesen compute it and *report* mismatches in the ROM
info panel, but they boot regardless. The field matters for ROM databases,
flash-cart menus, and good hygiene — not for booting. Reference for the format:
fullsnes (you already have it at `/home/chad/snesmanual/`) — see the "SNES
Cartridge ROM Header" section.

## C-Chip: concrete next steps with unidasm

The highest-leverage move now is to **disassemble the C-Chip firmware** — it
converts the single biggest unknown in the whole port into ~12 KB of readable
8-bit code. Steps, with the gotchas I found on your machine:

### 1. Get the two dumps (they are NOT on your disk yet)
I checked `/home/chad/superman-arcade/` — it has the 68K/gfx/sound ROMs but is
**missing both C-Chip firmware files**. So the project's original "not in our
ROM set" note was literally true *locally*, even though the dumps exist in the
world. You need:
- `b61_11.m11` — 8 KB external EPROM (Superman-specific), CRC `3bc5d44b`,
  SHA1 `6ba3ba35fe313af77d732412572d91a202b50542`. **It's 8 KB, not 2 KB.**
- `cchip_upd78c11.bin` — 4 KB uPD78C11 internal mask ROM (shared by all Taito
  C-Chip games), CRC `43021521`, SHA1 `73bc4b46cd2d6805ec926f39f22af00e38a3f822`.

Both ship in a complete MAME `superman` romset (the internal ROM lives in the
`cchip` device romset). **Verify the SHA1s before trusting them** — an optically
extracted mask ROM is exactly the kind of dump that can have bit errors.

### 2. Get a `unidasm` binary (your MAME checkout can't build it as-is)
Your `/home/chad/mame` is a **sparse checkout** — only `src/mame/taito/`
(247 files, no `src/devices/cpu/`, no `src/tools/`). So `unidasm` is neither
present nor buildable here. Options:
- Easiest: install a full MAME distribution; `unidasm` ships alongside it.
- From source: do a full MAME checkout and `make TOOLS=1` (builds `unidasm`).
- The uPD78C11 uses MAME's **`upd7810`** disassembler core. Confirm the exact
  arch token by running `unidasm` with no args (it prints the architecture
  list) and grepping for `upd78`.

### 3. Disassemble both ROMs at the correct base addresses
From `cchip_map` (taitocchip.cpp:181–187) the MCU address space is:
internal ROM `0x0000–0x0FFF`, SRAM window `0x1000–0x13FF`,
ASIC regs `0x1400–0x17FF`, external EPROM `0x2000–0x3FFF`. So:
```
unidasm cchip_upd78c11.bin -arch upd7810 -basepc 0x0000 > cchip_internal.dasm
unidasm b61_11.m11        -arch upd7810 -basepc 0x2000 > b61_11_eprom.dasm
```
(Flag names are the common unidasm spelling; if it complains, run `unidasm`
with no args for the exact usage — `-basepc`/`-arch` are the standard ones.)
The uPD78C11 boots into the **internal** mask ROM (per the MODE1=high wiring in
the chip notes), which then calls into the Superman EPROM — so read
`cchip_internal.dasm` for the entry/vector/handshake logic and
`b61_11_eprom.dasm` for the game-specific behavior.

### 4. What to extract from the disassembly
- The **self-test/handshake** path (matches the `0x401` ready/error register you
  already observed — that part of your protocol notes is real).
- What the MCU writes into the **8 KB shared SRAM** that the 68K later reads —
  these are the *data-producer* fields you must replicate (see RISK_CCHIP "triage").
- How it processes the **inputs** wired to its ports (PA=P1, PB=P2, AD=coins) —
  the C-Chip sits in the input path, so input handling is real logic, not a gate.

### 5. Validate with the same oracle discipline
Once you port the relevant logic to the SA-1, run a recorded MAME C-Chip
shared-RAM trace through your emulation and assert equality (RISK_CCHIP G3).
This reuses the exact MAME-as-oracle harness RISK_TRANSPILER.md calls for — build
it once, use it for both subsystems.
